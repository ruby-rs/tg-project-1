# Архитектура

## Задача

Прораб в течение дня присылает боту фото, текст и голосовые с объекта. Бот:

1. расшифровывает голосовые (Whisper — API или локально);
2. привязывает каждое сообщение к объекту и рабочей дате;
3. прогоняет текст, расшифровки и описания фото через LLM и собирает
   структурированный отчёт: что сделано, объёмы, проблемы, материалы, риски срыва сроков;
4. вечером отправляет руководителю сводку по всем объектам *(следующий этап)*;
5. хранит архив фото с датами и хешами — для споров с заказчиком и таймлапса.

## Компоненты

```
          Telegram
             │  long polling
             ▼
┌─────────────────────────┐        ┌──────────────────────────────┐
│  bot  (aiogram 3)       │        │  worker                      │
│  • регистрация, объекты │        │  • скачивает файл из TG      │
│  • приём сообщений ─────┼──┐  ┌──┼─▶• архив + SHA-256           │
│    (только запись в БД) │  │  │  │  • Whisper → расшифровка     │
│  • /report → задача ────┼──┤  │  │  • vision-LLM → описание фото│
└─────────────────────────┘  │  │  │  • LLM → отчёт в чат         │
                             ▼  │  └──────┬───────────────┬───────┘
                     ┌──────────┴───┐     │               │
                     │ PostgreSQL   │◀────┘               ▼
                     │ entries,     │              /data/media (том)
                     │ report_jobs  │
                     │ (данные и    │
                     │  очереди)    │
                     └──────────────┘
```

- **bot** — только быстрые операции: записать сообщение, поставить реакцию, ответить.
  `/report` лишь ставит задачу в `report_jobs` и отвечает «⏳ Формирую отчёт».
- **worker** — всё медленное и ненадёжное: скачивание файлов, Whisper, описание фото,
  сборка отчётов через LLM. Две независимые очереди (`entries` и `report_jobs`) со своей
  параллельностью: долгий запрос к LLM не задерживает расшифровку голосовых.
  Можно запускать несколько экземпляров.
- **PostgreSQL** — и хранилище, и очередь задач (`SELECT … FOR UPDATE SKIP LOCKED`).
  Отдельный брокер (Redis/RabbitMQ) на этом этапе не нужен: задачи переживают рестарт,
  ретраи с экспоненциальной задержкой, зависшие задачи подбираются по `locked_at`.
- **Медиа-архив** — локальный том на сервере в РФ. Файлы только добавляются, не
  перезаписываются; в БД хранится SHA-256. Позже — S3-совместимое хранилище
  (Yandex Object Storage, Selectel, VK Cloud) через тот же интерфейс `LocalFileStorage`.

## Поток данных

1. Прораб отправляет сообщение → хендлер `intake` создаёт `Entry`:
   `site_id` = текущий объект пользователя, `work_date` = дата в часовом поясе компании,
   `status` = `pending` (текст сразу `done`). Дубли апдейтов отсекаются уникальным
   ключом `(tg_chat_id, tg_message_id)`.
2. Если объект не выбран — сообщение всё равно сохраняется, бот спрашивает объект;
   после выбора все «ничьи» сообщения прораба привязываются к нему.
3. Воркер забирает `pending`, скачивает файл → `/data/media/{company}/{ГГГГ}/{ММ}/{ДД}/…`,
   фиксирует (commit) — файл в архиве, даже если дальше что-то упадёт.
   Затем расшифровывает голосовое / описывает фото и присылает прорабу расшифровку.
4. `/report` ставит задачу в очередь. Если голосовые за этот день ещё расшифровываются,
   воркер ждёт их до 10 минут, затем собирает все `done`-сообщения объекта за день
   в хронологический журнал (альбом фото — одна строка с общей подписью)
   `#id [ЧЧ:ММ] автор, тип: содержание`, отправляет в LLM со схемой JSON,
   валидирует ответ Pydantic-моделью (`SiteDailyReport`), при ошибке один раз просит
   модель исправить JSON. Отчёт сохраняется в `daily_reports` (JSONB), рендерится в HTML
   и отправляется в чат, откуда его запросили.
   Пункты отчёта ссылаются на `entry_ids` — это связь «вывод → фото/голосовое-доказательство»,
   которая понадобится для КС-2 и споров.

## Модель данных

| Таблица         | Назначение |
|-----------------|------------|
| `companies`     | Арендатор. Часовой пояс, код приглашения. Сюда же ляжет подписка. |
| `users`         | Пользователь Telegram, роль (`owner`/`manager`/`foreman`), текущий объект. |
| `sites`         | Строительные объекты компании, у каждого своя ссылка-приглашение. |
| `site_members`  | К каким объектам допущен прораб (руководитель видит все объекты компании). |
| `entries`       | Каждое сообщение: тип, дата, файл (путь, размер, SHA-256, EXIF-время), текст, расшифровка, описание фото + поля очереди. |
| `report_jobs`   | Очередь запросов отчёта: объект, дата, чат для ответа + поля очереди. |
| `export_jobs`   | Очередь выгрузок архива: объект, период, чат + поля очереди, итог (файлов, байт). |
| `report_feedback` | Оценки отчётов 👍/👎 и замечания — метрика качества. |
| `scheduled_runs`| Плановые рассылки компании за день (сводка, напоминание); уникальны по (компания, вид, дата). |
| `daily_reports` | Последняя версия отчёта по объекту за дату (JSONB). |

Даты:
- `sent_at` — время отправки по Telegram (для пересланных — время оригинала);
- `taken_at` — время съёмки из EXIF (только если фото отправлено «файлом»:
  Telegram вырезает EXIF у сжатых фото);
- `work_date` — рабочий день; `WORK_DAY_START_HOUR` позволяет отнести ночные
  досылки к предыдущему дню.

## Выбор провайдеров ИИ

Всё общение с моделями идёт через OpenAI-совместимый протокол (`openai` SDK с
`base_url`), поэтому провайдер меняется конфигом:

| Вариант | Расшифровка | Отчёты |
|---------|-------------|--------|
| Всё на своём сервере | `TRANSCRIBER=local` (faster-whisper) | vLLM / Ollama с открытой моделью (Qwen2.5, Llama 3.x) |
| Российское облако | свой Whisper-сервер | YandexGPT (OpenAI-совместимый API) или GigaChat через прокси `gpt2giga` |
| Зарубежное API | `TRANSCRIBER=api` | любой OpenAI-совместимый |

**152-ФЗ.** Голос и фото с людьми — персональные данные. Отправка их в зарубежный API
— трансграничная передача, требующая согласий и уведомления РКН. Для продакшена в РФ
рекомендуем локальный Whisper и российскую/свою LLM. Кроме того, ряд зарубежных API
блокирует запросы с российских IP.

Производительность локального Whisper на CPU (`small`, `int8`): голосовое на 1 минуту
расшифровывается за десятки секунд на 4 ядрах (зависит от процессора). `medium`/`large-v3` заметно точнее
на строительной лексике, но для них желателен GPU. Точность дополнительно повышает
подсказка со строительными терминами (`CONSTRUCTION_PROMPT`).

## Дорожная карта

1. **MVP (готово):** приём сообщений, привязка к объекту и дате, архив медиа,
   расшифровка, отчёт по `/report`.
2. **Вечерняя сводка (готово):** планировщик в воркере раз в минуту создаёт задачи
   в `scheduled_runs` по настройкам компании (`/settings`): напоминание прорабам без
   сообщений и сводку руководителям по всем объектам. Сводка берёт сохранённые
   отчёты, если они актуальны, и пересобирает остальные; под ней кнопки
   «📋 подробно». Дальше — кнопка «📷 фото дня».
3. **Подписка и пробный период (ЮKassa):** таблицы `subscriptions`, `payments`;
   тариф на компанию с лимитом объектов; мидлварь, проверяющая доступ;
   вебхук ЮKassa → отдельный HTTP-сервис (aiohttp) рядом с ботом; чеки по 54-ФЗ.
4. **КС-2:** справочник расценок/позиций сметы по объекту; LLM сопоставляет
   `work_done` с позициями сметы, накопление объёмов за период → генерация
   XLSX по унифицированной форме; ссылки `entry_ids` дают фотофиксацию к каждой строке.
5. **График работ:** загрузка графика (XLSX/MS Project), плановые объёмы по датам;
   сравнение с фактом из отчётов, прогноз отставания, риски в сводке.
6. **Архив и таймлапс:** выгрузка уже есть (`/archive`: ZIP по объекту за период с
   реестром `registry.csv`, `checksums.sha256` и сверкой хешей). Дальше — S3-хранилище,
   PDF-реестр, сборка таймлапса ffmpeg-ом по фото с одной точки.
7. **Эксплуатация:** вебхуки вместо polling, собственный Bot API сервер
   (файлы > 20 МБ), метрики. Уже есть: Redis для состояний диалогов, Sentry,
   CI на GitHub Actions, скрипт бэкапа `scripts/backup.sh`.
